# gitblog

메인 서비스 저장소: [gitblogapp/gitblog](https://github.com/gitblogapp/gitblog).

GitHub 저장소로 블로그를 만들고 글을 편집·배포하는 서비스입니다. 운영 주소는 https://gitblog.app 입니다. GitHub App 하나로 파일 편집, Pages 배포, Discussions 댓글을 연결합니다.

## 구성

- **gitblog Worker**: SvelteKit 웹사이트, GitHub 로그인, CMS, 템플릿 생성, Pages 설정, 공개 피드 API.
- **gitblog-giscus Worker**: [원본 giscus 포크](https://github.com/gitblogapp/gitblog-giscus)의 Next.js/React 위젯. `GISCUS` 서비스 바인딩을 통해 같은 도메인의 `/client.js`, `/widget`, 댓글 API를 제공합니다. 별도 공개 도메인은 없습니다.
- **D1 `gitblog`**: 블로그/게시글 색인, 클릭 집계, 검증된 댓글 지표, 수집 작업과 재시도 상태.
- **피드 반영**: 검증된 배포 알림은 응답 후 즉시 RSS를 수집합니다. 저장소별 D1 상태에 작업을 먼저 기록하므로 중단되어도 복구됩니다. Cloudflare Queues는 사용하지 않습니다.
- **Cron**: 5분마다 실패/중단된 피드 작업 최대 4개와 기존 탐색·댓글 작업 최대 8개를 처리합니다. 설치 저장소를 매시간 다시 확인하고, 정상 피드는 마지막 성공 후 24시간이 지나면 보완 수집합니다. 일일 보완 작업은 실행당 최대 10개를 예약하므로 대규모 목록에서는 더 늦어질 수 있습니다.

Supabase 서비스·키·SDK는 필요하지 않습니다. 이전 구현은 비교용으로 `legacy/supabase`에 보관하며 운영 런타임에서 사용하지 않습니다. 기존 운영 Supabase가 구성되지 않은 상태에서 D1을 새로 생성했습니다.

## 로그인과 생성

GitHub App 하나로 로그인·저장소 생성·편집·배포·댓글을 처리합니다. 별도 생성용 OAuth App은 사용하지 않습니다.

1. GitHub App 사용자 인증으로 로그인합니다. 로그인 토큰은 최대 8시간의 암호화된 HttpOnly 세션 쿠키로 유지하고 서버 DB에 저장하지 않습니다.
2. 처음에는 로그인한 **개인 계정**에 gitblog App을 설치합니다. **All repositories**와 **Only select repositories**를 모두 지원합니다. 선택 설치에서도 gitblog에서 생성한 새 블로그는 앱 접근 대상에 자동 추가됩니다. All repositories를 선택하면 앱 권한이 계정의 모든 저장소에 적용되지만, 블로그 목록·관리·피드는 아래 템플릿 검증을 통과한 공개 저장소만 대상으로 합니다.
3. 설치가 완료되면 Studio에서 이름을 입력하여 공개 블로그 저장소를 만듭니다. 사용자 토큰으로 현재 설치 접근을 확인하고, 계정 ID·앱 ID·개인 계정 여부·설치 정지 상태·권한을 다시 검증한 뒤 기존 GitHub App **사용자 토큰**으로 REST 템플릿 생성 API를 호출합니다. 생성용 설치 토큰을 발급하거나 로그인 토큰을 폐기하지 않습니다. 서버 비공개 키는 현재 설치 상태 재검증에 사용합니다.
4. 생성 후 기존 로그인 세션으로 새 저장소의 접근·ID·템플릿을 검증합니다. 접근이 확인되면 환경 변수, Discussions, Pages, Actions를 설정합니다. 새 저장소가 설치 접근 대상에 없으면 **생성한 저장소 연결하기**를 표시합니다. 사용자가 GitHub에서 Only select repositories를 유지하고 해당 저장소를 추가하면 설치 콜백 또는 **연결 확인 후 설정 계속하기**로 설정을 이어갑니다.
5. 자동 설정 실패 시 생성한 저장소와 실제 실패 단계를 보존하며, 다시 생성하지 않고 설정만 재시도합니다. 저장소 미연결과 다른 설정 오류를 구분해 안내합니다. 생성 자체의 결과를 받지 못한 요청은 자동 재실행하지 않습니다.

2026-10-07 실제 선택 설치에서 두 토큰을 비교했습니다. 설치 토큰으로 REST 템플릿 생성 시 자동 접근 추가가 누락됐지만, GitHub App 사용자 토큰으로 일반 저장소와 템플릿 저장소를 만들면 모두 기존 설치에 즉시 자동 추가됐습니다. 생성 경로는 사용자 토큰을 유지하며 별도 OAuth App이나 All repositories 전환이 필요하지 않습니다. GraphQL 템플릿 복제는 권한 오류가 발생해 사용하지 않습니다. 설치 범위에서 나중에 저장소를 제외하는 등 접근이 사라진 경우에는 기존 수동 연결 복구 기능을 유지합니다.

GitHub에 저장소가 전혀 없어도 All repositories로 앱을 설치한 뒤 Studio에서 첫 블로그를 만들 수 있습니다. Only select repositories를 원한다면 GitHub의 템플릿 생성 화면에서 첫 블로그 저장소를 만든 뒤 해당 저장소만 앱에 연결할 수 있습니다.

설치에 선택한 일반 저장소는 블로그 목록에 표시하거나 피드에 등록하지 않습니다. GitHub가 반환한 `template_repository`·`parent`·`source`가 설정된 템플릿과 일치하는 공개 저장소만 블로그로 취급합니다. 템플릿 원본·비공개·보관 저장소는 제외합니다.

Studio와 피드 수집은 설치 대상 목록을 확인한 뒤 GraphQL로 최대 50개씩 템플릿·포크 관계를 일괄 조회합니다. 저장소마다 REST 요청을 보내지 않아 All repositories에서 요청 수가 급증하는 것을 줄입니다. 관리·편집 작업에서는 해당 저장소의 접근 권한과 템플릿을 다시 검증합니다.

Studio는 독립적인 메타데이터 조회를 최대 2개씩 병렬 처리하고, 판별한 블로그 ID 목록을 Cloudflare Cache API에 5분간 보관합니다. 사용자·앱·설치·템플릿과 현재 접근 가능한 저장소 ID·이름을 캐시 키에 반영합니다. 설치 상태와 공개·쓰기 가능한 저장소 목록은 매번 GitHub에서 확인하므로 접근 해제·비공개 전환은 캐시보다 먼저 적용됩니다. 저장소 추가·삭제·이름 변경 시 키가 달라지며, **목록 새로고침** 또는 생성 직후 미완료 설정에서는 캐시를 건너뜁니다. 토큰·비공개 저장소·권한 판단·개인화 HTML은 캐시하지 않으며, Cache API를 사용할 수 없는 환경에서는 기존 실시간 조회로 동작합니다.

개별 블로그 관리 화면은 All repositories 설치의 계정·앱·정지 상태·쓰기 권한을 실시간 확인한 뒤 사용자 토큰으로 해당 저장소를 직접 조회합니다. 선택 설치는 대상 저장소를 찾을 때까지 페이지를 읽고 즉시 멈춥니다. 공개 여부·쓰기 권한·템플릿 관계는 계속 검사합니다. 개요 화면에서는 편집 전용 `.pages.yml`을 읽지 않으며, 편집과 설정 작업에서는 기존처럼 검사합니다. 관리 화면에는 게시글과 외부 블로그 초기 설정을 표시합니다. 댓글·Pages 배포 패널은 표시하지 않으며, 화면 진입 시 Pages 주소나 Actions 실행 상태도 조회하지 않습니다. 블로그 생성 시 댓글·Pages 자동 설정은 유지합니다.

Studio에서 생성 버튼을 누르면 즉시 내 블로그 목록으로 전환하고 생성 중 카드에 로딩 아이콘을 표시합니다. 자동 설정 응답까지 기다린 뒤, 접근이 확인된 블로그 카드에서 관리 링크를 활성화합니다. 실패한 카드는 오류와 입력 수정 또는 남은 설정 재시도 경로를 제공합니다. 생성·재시도·설치 콜백의 완료 위치는 `/studio` 목록입니다. 이 로딩 표시는 현재 페이지의 생성 요청에 대한 상태이며, 탭을 닫아도 계속되는 별도 작업 큐는 아닙니다.

Studio는 생성 성공 응답의 저장소 ID와 이름을 사용자·앱에 묶인 10분짜리 암호화 HttpOnly 쿠키로 기억합니다. GitHub 목록 반영이 늦으면 관리 링크가 없는 목록 반영 중 카드를 표시하고, 2·4·8·15·30초 간격으로 목록을 최대 5번 자동 확인합니다. 조회가 끝난 뒤 다음 확인을 예약하므로 요청이 겹치지 않으며, 화면을 떠나거나 목록에 나타나면 중단합니다. 새로 생성한 저장소가 캐시의 블로그 목록에 없으면 다시 판별하며, 목록에 반영된 새 블로그는 먼저 표시합니다. 생성 기록 자체는 접근 권한이나 설정 성공의 근거로 사용하지 않습니다.

대표 이미지와 글 커버를 첨부하면 브라우저 편집 창에서 전체 이미지 맞춤, 영역 자르기, 확대·드래그 위치 조정, 좌우·상하 여백과 배경색·투명을 선택할 수 있습니다. 대표 이미지는 512×512, 커버는 템플릿의 16:9 비율에 맞춘 1600×900 정지 WebP로 변환합니다(PNG 대체 지원). 편집 중에는 업로드하지 않으며, 커버는 적용 시, 대표 이미지는 생성·설정 저장 시 사용자 저장소에 저장합니다. 대표 이미지는 선택 사항이고, 편집 취소는 기존 첨부를 유지합니다. 생성 설정 실패 후 같은 화면에서 재시도할 때는 편집된 파일을 메모리에 유지해 다시 전송합니다.

블로그 생성 시 Discussions 댓글 연결, Pages·Actions 활성화, 환경 설정 저장, 첫 배포 요청까지 자동 실행합니다. 설정 커밋의 push workflow가 Pages 활성화보다 먼저 실행되지 않도록 활성화를 먼저 마칩니다. 생성 직후 404 응답이나 선택·전체 설치의 목록 반영 지연, Discussions 기본 카테고리 반영 지연은 읽기 작업만 1초·2초 후 최대 두 번 재확인합니다. 일반 권한 거부와 배포 요청 실패는 즉시, 연결 누락은 재확인 이후에 단계별 오류를 표시합니다. Pages 활성화와 실제 배포 완료는 별개이며, 배포 결과는 GitHub Actions에서 확인합니다.

생성된 저장소 정보는 사용자·앱에 묶인 암호화 쿠키로 1시간 유지합니다. 설치 도중 로그인 세션이 만료되면 원래 설치 콜백으로 복귀합니다. 외부 URL을 로그인 복귀 경로로 허용하지 않습니다.

## 블로그 설정

블로그 관리 → **블로그 설정**에서 제목·소개·작성자·주소·언어·릴리스·소셜 링크·Google 소유권 확인·피드 참여를 편집합니다. 공개 값만 `.env.production`에 커밋하며, 기존 댓글 ID·저장소 연결·사용자 정의 값은 보존합니다. 관리 권한과 최신 파일 SHA를 검사하므로 동시 수정을 덮어쓰지 않습니다. 커밋 후 템플릿의 push 워크플로가 배포합니다. 블로그 주소 변경은 DNS나 Pages 사용자 도메인을 변경하지 않습니다.

DeepL 키는 별도 입력 폼에서 GitHub 공개키로 libsodium 호환 sealed box 암호화하여 해당 저장소의 Actions Secret `DEEPL_API_KEY`로 저장합니다. 키를 DB·쿠키·저장소 파일에 저장하거나 오류 응답으로 돌려주지 않습니다. 읽기 화면은 등록 여부만 확인하며 키 값을 읽을 수 없습니다. 키 변경 자체는 배포를 시작하지 않고 다음 번역 실행부터 적용됩니다. Secrets 권한이 없는 설치에서도 공개 설정은 사용할 수 있습니다. 키 삭제·기타 Secrets 관리는 GitHub 링크에서 진행합니다.

## 글 저장과 배포 진행

Studio에서 새 글을 작성하거나 수정해 저장하면 `/studio/[owner]/[repo]/publish`로 이동합니다. 저장 응답의 커밋 SHA에 해당하는 기본 브랜치의 `deploy.yml` 실행을 추적하여 저장 → 빌드 → Pages 배포 상태를 약 8초마다 갱신합니다. 완료되면 실제 Pages 주소를 기준으로 글 보기 링크를 표시하며, 초안은 공개 링크를 표시하지 않습니다. 완료 표시는 GitHub의 배포 작업 성공을 기준으로 하며 사이트 캐시 반영까지 잠시 걸릴 수 있습니다.

연속 저장으로 실행이 취소되면 저장한 커밋을 포함하는 후속 실행을 추적합니다. 후속 실행에서 글이 수정·삭제된 경우 저장 당시 글의 게시 성공으로 표시하지 않습니다. API 오류는 재확인하며, 숨겨진 탭에서는 조회를 멈추고 최대 20분 이후에는 수동 재확인을 제공합니다. 조회마다 로그인·저장소 접근 권한을 재검증하고 응답을 공유 캐시하지 않습니다. 일반 게시글 목록에서는 배포 상태를 조회하지 않습니다.

## GitHub App

등록명은 `gitblog.app`, slug는 `gitblog-app`입니다. `gitblog` 등록명은 다른 App이 사용 중이며 서비스 브랜드는 **gitblog**입니다.

- Homepage: `https://gitblog.app`
- Callback: `https://gitblog.app/auth/github/callback`
- 추가 개발 Callback: `http://127.0.0.1:5178/auth/github/callback`
- Setup: `https://gitblog.app/auth/github/setup`
- Redirect on update: 활성화
- Webhook: Active, `https://gitblog.app/api/github/webhook`, Content type `application/json`. 별도 무작위 Secret을 GitHub 설정과 Workers의 `GITHUB_WEBHOOK_SECRET`에 동일하게 등록합니다. Repository 이벤트를 구독합니다. 설치 해제·저장소 선택 해제는 삭제로 취급하지 않습니다.
- Contents, Administration, Actions, Pages, Discussions: Read & Write; Metadata: Read
- Pull requests, Workflows: Read & Write (템플릿 업데이트 PR 준비에 필요하며 기존 설치도 추가 권한을 승인해야 합니다.)
- Secrets: Read & Write (Studio에서 DeepL 키를 저장할 때 필요하며, 기존 설치도 추가 권한을 승인해야 합니다.)
- 사용자 토큰 만료: 활성화. 설치 시 별도 사용자 OAuth 요청: 비활성화.

환경 설정은 실행 환경에 따라 다음 위치에서 관리합니다.

| 실행 환경 | 일반 설정 | 비밀값 |
| --- | --- | --- |
| 로컬 Vite (`bun run dev`) | `.env.example`을 복사한 `.env` | 같은 `.env`에 입력, Git 제외 |
| 로컬 Workers (`wrangler dev`) | `wrangler.jsonc`의 `vars`와 로컬 실행에 필요한 URL 재정의 | `.dev.vars`, Git 제외 |
| 운영 Workers | `wrangler.jsonc`의 `vars` | Workers Secrets |

`.env`는 로컬 개발용이며 운영 배포 설정으로 복사하지 않습니다. `.dev.vars`에는 로컬 Worker 실행에 필요한 비밀값을 모두 입력하고, 개발용 URL을 사용할 때는 `PUBLIC_SITE_URL`·`GITHUB_CALLBACK_URL`도 함께 재정의합니다. 운영에는 파일 경로인 `GITHUB_APP_PRIVATE_KEY_PATH` 대신 PEM 내용인 `GITHUB_APP_PRIVATE_KEY`를 Secret으로 등록합니다. 서비스 이름은 코드에서 `gitblog`로 고정합니다.

`AUTH_SECRET`은 32자 이상이며 두 Worker가 공유합니다. gitblog는 `GITHUB_APP_PRIVATE_KEY`, giscus는 `GITHUB_PRIVATE_KEY` 이름으로 같은 App PEM을 사용합니다.

### 배포 절차

Cloudflare Workers Builds가 `gitblogapp/gitblog`의 `main` 브랜치에 연결되어 있습니다. `main`에 푸시하면 아래 검사를 모두 통과한 뒤 `gitblog` Worker와 `https://gitblog.app`에 자동 배포합니다.

- Root directory: `/`
- Build command: `bun install --frozen-lockfile && bun run check && bun run test && bun run lint && bun run build`
- Deploy command: `bunx wrangler d1 migrations apply gitblog --remote && bunx wrangler deploy`
- Build variables: `BUN_VERSION=1.3.14`, `SKIP_DEPENDENCY_INSTALL=true` — 고정한 Bun 버전으로 빌드 명령에서 의존성을 설치합니다.
- Preview builds: 비활성화

로컬과 CI의 패키지 관리자는 Bun 1.3.14로 통일합니다. `package.json`의 `packageManager`와 Cloudflare의 `BUN_VERSION`을 함께 관리합니다. 의존성 변경 시 `bun add`/`bun remove`로 `bun.lock`을 갱신하고 커밋합니다. `package-lock.json`은 사용하지 않습니다. 테스트는 Vitest를 실행하는 `bun run test`를 사용하며, 커밋 전 위 Build command로 설치부터 빌드까지 확인합니다.

빌드 연결 설정과 배포 토큰은 Cloudflare의 Worker → Settings → Builds에서 관리합니다. 운영 Secrets는 기존 Worker 설정을 사용합니다. 운영 배포는 미적용 D1 마이그레이션을 먼저 실행하고, 성공한 경우에만 Worker 코드를 배포합니다. 배포 토큰에는 D1 편집 권한이 필요합니다. 마이그레이션이 실패하면 배포도 중단됩니다. `bun run deploy`로 로컬에서 배포할 때도 같은 순서를 따릅니다. 별도 `gitblog-giscus` Worker 배포는 자동화 대상에 포함되지 않습니다.

새 테이블이나 컬럼을 사용하는 코드를 배포할 때는 해당 마이그레이션을 함께 커밋합니다. 마이그레이션 적용 중에는 이전 Worker가 계속 서비스하므로, 기존 코드와 호환되는 스키마 변경부터 적용해야 합니다. 예를 들어 프로필 테이블이 없는 상태에서 새 코드만 배포하면 글 목록 조회가 503으로 실패합니다.

```sh
bun install --frozen-lockfile
cp .env.example .env
bunx wrangler d1 migrations apply gitblog --local
bun run dev -- --host 127.0.0.1 --port 5178
bun run check
bun run lint
bun run test
```

실제 서비스 바인딩을 포함한 검증은 두 Worker의 `wrangler dev`를 함께 실행합니다. 현재 댓글 북마크 기능의 운영 배포 순서는 D1 migration → gitblog → gitblog-giscus입니다.

```sh
bun run deploy
# 이후 ../gitblog-giscus에서 npm ci && npm run deploy (별도 저장소의 기존 방식 유지)
```

gitblog Secrets: `AUTH_SECRET`, `GITHUB_APP_CLIENT_SECRET`, `GITHUB_APP_PRIVATE_KEY`. giscus Secrets: `AUTH_SECRET`, `GITHUB_PRIVATE_KEY`. App ID와 Client ID는 공개 설정입니다. Secret은 `wrangler secret put`/`secret bulk`의 stdin으로 전달하고 Git이나 명령행 인수에 넣지 않습니다.

로컬 RSS 테스트 데이터는 `bun run import:local -- ../svelte-gitblog-template/build/rss.xml`로 가져올 수 있습니다. 이 명령은 로컬 D1에만 씁니다.

## 피드와 지표

공개 RSS에는 제목·발췌만 저장하며 클릭은 원문으로 연결합니다. manifest는 GitHub API로 확인한 Pages 주소와 저장소 ID가 일치해야 합니다. 다른 호스트·경로와 리다이렉트를 거부하고 응답 크기를 제한합니다. 등록할 때 비공개·보관 저장소를 거부합니다. GitBlog App 설치 해제는 공개 피드 구독을 중단하지 않습니다. 수집 중단은 `PUBLIC_HUB_ENABLED=false`로 재배포하여 manifest에 반영합니다. 이미 등록된 블로그는 다음 알림 또는 일일 보완 수집에서 비활성화됩니다.

- 최신 글: 게시 시간순. 언어 미지정 시 원문 언어 한 개만 선택합니다.
- 인기 글: 일별 고유 클릭; 1일/7일/30일/전체.
- 트렌딩: 최근 72시간 글의 클릭과 GitHub에서 검증한 댓글 작성자·댓글 수, 시간 감쇠.
- 클릭: 봇/미리보기 제외, 방문자 일별 중복 제거, 네트워크 일별 상한. 원 IP는 저장하지 않으며 일별 HMAC 값을 사용합니다. 세부 집계는 31일, 전체 누적 합계는 계속 보관합니다.
- 댓글 힌트: GitHub에서 저장소·Discussion·댓글·작성자를 다시 확인한 후 반영합니다. 사용자가 보낸 본문이나 작성자를 신뢰하지 않습니다. 삭제도 GitHub 재확인을 거칩니다.
- 작업: D1 원자적 임대, 중복 합치기, 지수 재시도 5회. 실패 작업은 `jobs.last_error`에서 확인하고 7일 보관합니다. 재시도는 해당 작업의 `attempts=0`, `available_at=0`으로 운영자가 명시적으로 초기화합니다.

목록은 D1 SQL로 읽으며 랭킹은 집계 테이블에서 계산합니다. 대규모 트래픽으로 확장할 때는 별도 랭킹 스냅샷과 캐시를 추가할 수 있습니다.

## 화면 언어

서비스 화면은 한국어(`ko`)와 영어(`en`)를 지원합니다. 상단에서 언어를 선택하면 즉시 변경되며, 선택은 `gitblog_language` 쿠키에 1년간 저장합니다. 저장된 선택이 없으면 `Accept-Language`의 우선순위와 지역 코드(`ko-KR`, `en-US` 등)를 읽고, 지원 언어가 없으면 영어를 사용합니다.

화면 언어는 게시글 필터의 `locale`과 별개입니다. 글 본문·제목·태그 및 저장소 콘텐츠는 번역하거나 수정하지 않습니다. JavaScript가 켜져 있으면 언어 변경 시 페이지 전체를 새로 열지 않아 작성 중인 글을 유지합니다. JavaScript 없이도 언어 변경 폼을 제출할 수 있습니다.

번역 카탈로그는 `src/lib/i18n/en.json`이며 한국어 원문을 키로 사용합니다. `{0}`, `{1}` 자리표시자로 사용자 데이터를 삽입하고 HTML로 실행하지 않습니다. 화면은 요청별 언어로 서버 렌더링하며, 언어·사용자별 HTML과 SvelteKit 데이터 응답은 공유 캐시를 사용하지 않습니다. 공개 피드 API와 정적 자산의 캐시는 유지됩니다.

메인 화면의 전체·최신·인기·트렌딩·블로그 탭은 URL 이동 없이 표시 목록을 전환합니다. 더 보기와 재시도도 화면 안에서 처리하고, 탭을 오가거나 화면 언어를 바꿔도 선택한 탭과 추가로 불러온 목록을 유지합니다. 상단의 메뉴는 기존처럼 각 목록 페이지로 이동합니다.

## 독자 보관함

`/library`에서 GitHub 로그인 사용자의 북마크와 최근 본 글을 관리합니다. PostCard의 북마크와 GitBlog giscus 위젯은 같은 D1 데이터를 사용하며, 저장소 설치 없이 독자 로그인으로 이용할 수 있습니다. 최근 본 글은 GitBlog의 `/go/:postId`를 통해 원문으로 이동한 경우에만 기록합니다. 검색 등으로 원문에 직접 방문한 기록이나 완독 여부는 수집하지 않습니다. 기록은 본인만 볼 수 있고 일시 정지·개별 삭제·전체 삭제할 수 있습니다.

- `bookmarks`, `reading_history`: GitHub 사용자 ID + 언어와 무관한 고정 글 ID로 중복 방지. 일시적으로 접근할 수 없는 글은 개인 목록의 스냅샷을 유지하지만, Studio에서 삭제한 글은 모든 독자의 스냅샷을 비우고 ‘삭제된 글’로 표시합니다.
- `reader_preferences`: 최근 본 글 기록 여부. GitHub 토큰은 이 테이블들에 저장하지 않습니다.
- `github_profiles`: 저장소 소유자(조직 포함)의 공개 GitHub 프로필을 계정별로 공유합니다. 대소문자가 다른 같은 로그인과 여러 블로그·언어별 카드·북마크·읽은 글 목록은 동일한 최신 프로필을 사용합니다. 조직 블로그는 개인 작성자가 아닌 조직 프로필을 기본 표시합니다.
- 프로필은 계정별 24시간 캐시를 사용하며, 동시 갱신은 하나의 요청으로 합칩니다. 앱 연결 시 일시적인 설치 토큰을 사용하고, 앱 없는 공개 RSS 수집은 인증 없는 GitHub 공개 프로필 API를 사용합니다. 프로필 API 오류·한도 초과는 글 수집을 막지 않으며 기존 프로필을 유지합니다. 실패 후 최소 1시간이 지난 다음 피드 수집 또는 앱 탐색에서 재시도합니다. 접근 토큰은 DB에 저장하지 않습니다.
- `/v1/me/bookmarks`: GitBlog 세션으로 글 카드 상태를 일괄 조회하고 북마크를 변경합니다.
- `/v1/reader/bookmarks`: 저장소에 한정된 기존 giscus 인증으로 글의 북마크 상태 조회·변경만 허용합니다. 새 인증에는 서버가 확인한 사용자 ID를 포함하고, 이전 인증은 유효기간 내 GitHub에서 사용자를 확인하여 계속 사용할 수 있습니다.

메인 Worker의 배포 명령이 `0002_blog_profiles.sql`, `0003_reader_library.sql`, `0010_account_profiles.sql`을 포함한 미적용 마이그레이션을 먼저 적용합니다. `0010`은 기존 블로그별 프로필 중 계정별 최신 데이터를 이관하며 이전 Worker 요청이 끝날 수 있도록 `blog_profiles` 테이블은 남겨 둡니다. 이어 `gitblog-giscus` Worker를 배포합니다. 프로필은 다음 피드 동기화에서 채워집니다. 기존 GitBlog 댓글 호스트를 사용하는 블로그는 템플릿 수정 없이 북마크 UI를 받습니다.

## 글 삭제

Studio의 기존 글 편집 화면에서 **삭제 대상 확인**을 선택합니다. 원문과 `content/translations/<locale>/posts/<같은 파일명>`에 있는 번역본 목록을 확인하고 파일명을 입력해야 삭제할 수 있습니다. 서버는 GitHub App 설치·사용자 쓰기 권한을 다시 확인하며, 확인 당시의 브랜치 HEAD와 원문 SHA가 바뀌면 중단합니다. 원문과 번역본은 하나의 삭제 커밋으로 반영하고 강제 푸시는 사용하지 않습니다. 기존 템플릿도 별도 수정 없이 이용할 수 있으며, 커밋 후 기존 배포 workflow가 실행됩니다.

`0004_post_deletions.sql` 마이그레이션이 필요합니다. 삭제 시 글의 모든 언어별 피드 데이터·댓글 집계·클릭 집계를 지우고, 모든 독자의 북마크·읽은 기록에서 제목·요약·주소를 포함한 스냅샷을 제거합니다. 개인 목록에는 삭제된 글의 ID와 저장/방문 시각만 남습니다. 삭제 표식은 이전 RSS나 늦게 도착한 북마크 요청이 정보를 다시 저장하는 것을 차단합니다. 같은 글 ID를 Git에서 복원해도 자동 재등록되지 않으므로, 다시 발행하려면 새 글 ID를 사용해야 합니다.

GitHub와 D1 사이의 중단에 대비해 커밋 SHA·저장소·경로·처리 상태만 `post_deletions`에 먼저 기록합니다. 사용자 토큰과 글 본문은 저장하지 않습니다. GitHub 응답이나 DB 정리가 중단되면 완료로 표시하지 않고 확인 중 상태를 보여 줍니다. 5분 주기의 Cron이 저장소 하나의 Contents 읽기 권한만 가진 설치 토큰으로 삭제 커밋이 대상 브랜치에 포함되었는지 확인한 뒤 정리를 완료합니다. 설치가 해제되어 검증할 수 없으면 확인 중 상태를 유지합니다.

이 기능은 **일반 삭제**입니다. 과거 Git 이력, GitHub Discussions, Releases, 공유 이미지, 외부 사본은 제거하지 않습니다. 공개 사이트의 내용은 재배포 완료 후, 이미 캐시된 피드 응답은 캐시 만료 후 사라집니다. 배포가 실패하면 GitHub Actions에서 재시도해야 합니다. GitHub나 Pages CMS에서 직접 삭제한 글은 기존 피드 누락 처리 정책을 따르며, Studio의 명시적 삭제와 동일한 스냅샷 정리를 수행하지 않습니다.

### Git 이력에서 글 제거

Studio의 글 삭제 화면에서 **Git 이력도 제거하려면 분석하기**를 선택합니다. 일반 삭제를 완료한 화면에서도 **Git 이력에서 제거**로 이어갈 수 있습니다. 저장소 관리자만 사용할 수 있으며, 분석 결과(파일 경로·브랜치·태그·변경 커밋 수)를 확인하고 `owner/repository/filename.md`와 확인 체크박스를 제출해야 실행합니다. 분석은 30분 동안 유효합니다.

실행은 **대상 블로그 저장소의 GitHub Actions**에서 처리합니다. 템플릿의 `.github/workflows/post-history.yml`이 공개 템플릿 저장소(`gitblogapp/svelte-gitblog-template`)의 `post-history-worker.yml`을 특정 커밋 SHA로 고정해 호출합니다. 실행 기록·로그·Actions 사용량은 블로그 저장소에 속하며, GitBlog App도 해당 블로그에만 설치하면 됩니다. `gitblogapp/gitblog`에 App을 설치하거나 블로그에 App 비공개 키·PAT를 저장할 필요는 없습니다. 작업은 고정된 공개 실행 코드만 체크아웃하며 블로그 안의 스크립트는 실행하지 않습니다.

운영 준비:

1. 템플릿 저장소의 실행 코드·재사용 워크플로·caller 커밋을 **먼저 공개 원격에 푸시**합니다. 승인된 커밋은 `src/lib/server/history/runner-version.ts`에 고정되어 있고, 템플릿 caller의 `uses` SHA와 일치해야 합니다. 실행 코드를 업데이트할 때는 템플릿의 공개 실행 코드 → 템플릿의 재사용 워크플로 → 템플릿 caller와 서버의 승인 SHA 순서로 발행합니다.
2. 템플릿을 발행하고 `0005_history_purges.sql`까지 D1 마이그레이션을 적용해 Worker를 배포합니다. 기존 `bun run deploy` 및 Workers Builds 명령이 배포 전에 마이그레이션을 적용합니다.
3. 새 블로그는 템플릿에서 실행 워크플로를 받습니다. **기존 블로그는 최신 템플릿의 `.github/workflows/post-history.yml` 파일을 기본 브랜치에 추가**해야 합니다. 이미 파일이 있으면 기존 변경을 검토해 병합합니다. 워크플로가 없거나 버전이 다르면 Studio가 업데이트를 안내합니다.
4. 대상 블로그에서 Actions를 활성화하고 공개 `gitblogapp/svelte-gitblog-template` 재사용 워크플로 호출을 허용합니다. 해당 블로그의 GitBlog App에는 기존 Contents·Actions 쓰기 권한이, 요청자에게는 관리자 권한이 필요합니다. App 비공개 키는 기존 Workers Secret만 사용합니다.
5. 실행 워크플로는 운영 `gitblog.app`을 호출합니다. 로컬 DB에 만든 작업은 운영 콜백과 연결되지 않습니다. 다른 서비스 도메인으로 포크할 때는 템플릿의 `scripts/history/run.py`의 origin, 서버의 OIDC audience, 공개 재사용 워크플로와 승인 SHA를 함께 변경합니다.

분석은 전체 브랜치·태그의 Markdown 파일에서 글의 고정 ID를 찾고, 동일 파일명의 번역본과 Git이 감지한 이름 변경 경로를 포함합니다. ID가 없던 시절에 이름과 내용이 모두 크게 바뀐 파일이나 별도로 복사한 문서는 자동으로 연결할 수 없습니다. 같은 경로가 다른 글 ID에 사용되었거나 게시글 폴더 밖으로 이동한 경우에는 자동 처리를 거부합니다. 최대 100개 참조, 5,000개 커밋, 20,000개 Markdown blob, 500,000개 트리 항목, 500개 제거 경로를 지원하며 초과하면 중단합니다.

확인 후 같은 분석을 다시 실행해 결과가 일치하는지 검사하고 `git push --atomic`과 참조별 `--force-with-lease=<ref>:<old SHA>`로 한 번에 반영합니다. 무조건적인 force/mirror push, 브랜치 보호 해제, PR 참조 변경은 하지 않습니다. 브랜치·태그 보호 규칙이나 권한이 거부하면 사용자가 설정을 검토해야 합니다. 커밋/태그 서명이 사라질 수 있고 이후 커밋 SHA가 바뀝니다. 협업자는 새로 clone하거나 안전하게 rebase해야 하며 옛 브랜치를 merge하면 삭제한 내용이 돌아올 수 있습니다.

GitHub OIDC 서명·issuer·audience·대상 블로그의 저장소 ID·caller 경로와 분석 당시 커밋 SHA·이벤트·run ID/attempt를 검증하고, `job_workflow_ref`와 `job_workflow_sha`가 승인된 재사용 워크플로의 정확한 SHA인지 확인한 작업에만 해당 블로그 하나로 제한된 설치 토큰을 줍니다. 사용자 토큰은 DB에 저장하지 않습니다. 분석 토큰은 읽기 전용이며, 확인한 제거 작업에만 Contents 쓰기를 허용합니다. 설치 토큰은 작업 종료 시 폐기를 시도하며, 강제 중단되더라도 GitHub의 짧은 유효기간이 지나면 만료됩니다. 재실행된 Actions 작업은 승인하지 않습니다.

push 전에 승인된 참조 변경표를 D1에 기록하고, 실제 모든 브랜치·태그가 결과와 일치하거나 브랜치가 제거 결과 위에 후속 커밋을 추가한 것이 확인된 뒤에만 글 ID의 삭제 표시를 확정합니다. 이때 기존 삭제 기능과 동일하게 피드, 모든 독자의 북마크·읽기 기록 snapshot, 집계 데이터를 정리합니다. 다른 글의 고정 ID와 북마크는 유지됩니다. 콜백 유실은 상태 화면과 5분 주기 작업이 복구합니다. 동시 변경으로 결과가 달라지면 성공으로 표시하지 않고 검증 대기 상태를 유지합니다. 종료된 작업의 검증이 계속 대기하면 관리자가 실제 refs와 실행 로그를 점검해야 합니다. 완료 후 재배포를 요청하며 재배포 실패 여부는 별도로 표시합니다.

실행 요청이 명확히 거절되면 즉시 실패 사유를 표시합니다. 응답 유실·서버 오류는 중복 실행 없이 GitHub 실행 기록으로 확인합니다. 상태 화면은 5초 후부터 10초마다 자동 갱신하며, 숨긴 탭에서는 조회를 쉬고 완료되면 중단합니다. GitHub 작업 실패·취소·콜백 누락은 화면에서 감지합니다. 실행 기록이 10분 동안 없으면 다시 분석할 수 있도록 실패 처리하며, 이미 push를 준비한 검증 대기 작업은 이 방식으로 종료하지 않습니다.

**제거 범위:** 선택한 Markdown 경로의 모든 버전을 브랜치·태그에서 제거합니다. 커밋 메시지에 직접 적은 본문, Discussions 댓글, Releases 본문/첨부, 공유 이미지, 과거 Actions artifacts/배포, PR 참조, 외부 clone/fork, 검색엔진·GitHub 캐시는 삭제하지 않습니다. GitHub에서 객체 자체가 즉시 사라지는 것을 보장하지 않습니다. 민감한 데이터의 캐시 제거는 [GitHub 공식 안내](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)를 따릅니다.

실제 Git 변경 검증은 운영 저장소 대신 임시 bare 저장소에서 수행합니다:

```sh
cd ../svelte-gitblog-template
python3 -m venv /tmp/gitblog-history-venv
/tmp/gitblog-history-venv/bin/pip install -r scripts/history/requirements.txt
PATH="/tmp/gitblog-history-venv/bin:$PATH" bun run test:history
cd ../gitblog
bun run test
```


## Studio 템플릿 업데이트

블로그 관리 → **템플릿 업데이트**에서 안정 버전 확인 → 변경 분석 → 업데이트 PR 준비 → Actions 검증 → 확인 후 적용 순서로 진행합니다. 대상 블로그 저장소의 관리자만 사용할 수 있습니다. GitBlog App은 대상 블로그에만 설치하며, 추가 PAT나 서버에 저장하는 사용자 토큰은 필요하지 않습니다.

템플릿의 기본 브랜치에 있는 `.gitblog/release.json`이 안정 버전과 **정확한 커밋 SHA**를 가리킵니다. `main`의 아직 발행하지 않은 코드 변경은 업데이트에 포함하지 않습니다. 템플릿 유지보수자는 코드 변경과 `bun run update:check` 검증을 먼저 완료하고 커밋한 뒤, 별도 커밋에서 release의 `version`·`revision`을 갱신합니다. 서비스와 템플릿의 미푸시 커밋을 먼저 공개한 뒤 기능을 사용해야 합니다.

처음 업데이트하는 템플릿 생성 블로그는 최초 생성 커밋의 파일을 기준으로 삼습니다. 이후에는 업데이트 PR에 저장된 `.gitblog/template.json`의 공식 템플릿 revision을 기준으로 비교합니다. 버전 기록의 사용자 정의 필드는 보존합니다. Fork의 생성 기준, 여러 root 이력, 500개 이상 커밋의 최초 버전을 자동 추측하지 않습니다. 이 경우 관리자가 실제 기준이 된 공식 템플릿 SHA를 검토하고 다음 파일을 기본 브랜치에 등록한 뒤 다시 분석해야 합니다. 임의로 최신 SHA를 넣으면 올바른 비교 기준이 되지 않습니다.

```json
{
  "schemaVersion": 1,
  "repository": "gitblogapp/svelte-gitblog-template",
  "version": "1.0.0",
  "revision": "실제로 적용한 공식 템플릿의 40자리 커밋 SHA"
}
```

이전 공식 파일·현재 블로그·새 공식 파일을 **파일 단위로** 비교합니다. 수정하지 않은 공식 파일의 추가·변경·삭제만 반영하고, 사용자 추가 파일과 원문·번역·미디어·환경 설정·CMS·테마·확장을 보존합니다. 이전·현재·새 템플릿의 preserve 규칙을 합쳐 적용하며 기본 보호 경로를 축소할 수 없습니다. 양쪽에서 수정한 코드, 의존성, lockfile, 워크플로는 자동 줄 병합 없이 충돌로 표시합니다. GitHub에서 사용자 변경을 보존해 병합한 뒤 다시 분석해야 합니다. 테마 분리 이전 구조, 테마/확장 API 변경, 이진 파일·symlink·대규모 변경은 별도 마이그레이션 대상으로 중단합니다. 코드 검증만으로 사용자 화면의 시각적 동일성을 보장하지 않습니다.

분석 결과와 승인 커밋 SHA·PR 번호만 D1 `0006_template_updates.sql`에 저장합니다. 소스 본문·비밀키·GitHub 토큰을 DB에 저장하지 않습니다. 준비 중 연결이 끊기면 같은 작업에서 재시도하여 기존 브랜치와 PR을 재사용합니다. 기본 브랜치는 준비 단계에서 변경하지 않으며, 브랜치를 force push하지 않습니다. 작업 종료는 열려 있는 PR을 닫고 새 분석을 허용합니다. 이미 외부에서 병합한 코드를 되돌리거나 브랜치를 삭제하지 않습니다.

적용 전 현재 관리자 권한, 저장된 PR의 저장소·브랜치·head SHA, 분석 당시 기본 브랜치 SHA, 공식 `validate-update.yml`의 해당 PR 실행 성공과 실제 validate job 성공, GitHub의 clean 병합 상태를 다시 확인합니다. 분석 후 새 글 작성 또는 PR 브랜치 변경 시 다시 분석해야 합니다. 승인한 head SHA로만 병합하고, 저장소의 기존 push 배포 워크플로가 재배포합니다. GitBlog는 준비 과정에서 번역·ID 생성·발행 명령을 호출하지 않습니다. 사용자가 추가한 push/PR 워크플로가 있다면 그 실행 규칙도 적용되므로 검토해야 합니다.

운영 준비: D1 migration 0006 적용, GitBlog App의 **Pull requests·Workflows 쓰기** 권한 추가와 설치 승인, Actions 실행 허용, 서비스 및 템플릿 발행. `Actions` 쓰기와 `Workflows` 쓰기는 서로 다른 권한입니다. 빌드에서 자동 마이그레이션을 적용하는 기존 배포 명령을 그대로 사용합니다.


## 블로그 등록과 배포 후 피드 갱신

세 경로를 GitHub 저장소 ID 하나로 합칩니다. 웹에서 저장소가 생성되면 즉시 D1에 `pending` 상태로 등록하고, 기존 Studio 생성 기록으로 내 목록에도 바로 표시합니다. 댓글·Pages 연결이 실패해도 이미 생성한 저장소를 다시 만들지 않습니다. 공개 목록에는 유효한 배포 manifest와 RSS를 확인한 뒤 `active`로 노출합니다.

앱 없이 공식 템플릿을 사용한 블로그도 배포 후 자동 등록할 수 있습니다. 템플릿의 `register` 작업이 공식 `register-blog.yml`을 고정 커밋으로 호출합니다. 이 작업은 호출 저장소의 임시 `GITHUB_TOKEN`으로 공개 여부·공식 템플릿/포크 관계·기본 브랜치·Pages 주소를 확인하고 GitHub Actions OIDC 증명을 전송합니다. 서버는 서명, audience, 저장소 ID 및 공식 워크플로의 고정 SHA를 검증합니다. GitHub 접근 토큰은 서버로 보내거나 저장하지 않습니다. 고정된 등록 작업에서 블로그의 코드를 실행하지 않는 것이 신뢰 경계입니다.

- `.env.production`의 `PUBLIC_HUB_ENABLED=true`, `PUBLIC_HUB_URL=https://gitblog.app`을 사용합니다. GitHub Actions 정책에서 공식 템플릿의 재사용 워크플로와 `id-token: write`를 허용해야 합니다.
- 첫 알림 전송 실패는 워크플로에서 최대 4회 재시도합니다. 모두 실패하면 Actions의 **Sync GitBlog feed**를 수동 실행하거나 다음 배포로 다시 등록합니다. 앱도 없고 성공한 알림도 없는 저장소는 자동으로 발견할 수 없습니다.
- GitBlog App이 설치된 공식 템플릿·포크 저장소는 기존 매시간 탐색으로도 등록됩니다. 한 번 Pages 주소가 검증되면 공개 RSS 갱신에는 앱 설치가 필요하지 않습니다.
- 예전 템플릿의 인증 없는 알림은 이미 등록된 저장소에 한해 계속 처리합니다. 앱 없는 최초 등록에는 새 템플릿 워크플로가 필요합니다.
- 검증된 알림은 저장소별 분당 12회로 제한합니다. 기존 익명 알림의 전역 분당 30회 제한을 공유하지 않습니다. 같은 실행의 재전송은 중복 작업을 만들지 않습니다.
- 배포 커밋을 manifest와 각 RSS에 넣어 CDN에 이전 결과가 남은 경우 성공으로 오인하지 않습니다. 새 알림이 도착하면 이전 수집 결과의 저장을 차단하고 최신 배포를 처리합니다.
- 실패한 수집은 D1에 남겨 2분부터 최대 6시간 간격으로 재시도합니다. 변경 없는 글은 다시 쓰지 않고, 일일 보완 수집은 ETag/Last-Modified를 사용합니다. 비용은 기존 Workers 요청·CPU와 D1 읽기·쓰기 사용량에 포함되며 무료 사용량을 보장하지는 않습니다.

`0007_blog_ingestion.sql`을 Worker 배포 전에 적용해야 합니다. 기존 등록 블로그의 수집 상태도 이 마이그레이션으로 이어집니다. `0008_ingestion_indexes.sql`은 복구할 작업과 정상 피드의 인덱스를 나눠 정기 실행의 DB 읽기를 줄입니다. 등록 워크플로의 신뢰 SHA를 바꿀 때는 공개 템플릿에 먼저 커밋을 게시하고 서버의 `ingestion-identity.ts` 승인 SHA와 새 템플릿 호출부를 함께 갱신합니다.


RSS에서 사라진 글은 모든 언어 피드의 검증이 성공한 수집에서 즉시 `removed`로 숨깁니다. RSS 오류·부분 수집 실패·이전 배포 커밋은 삭제 근거로 사용하지 않습니다. 일반적인 RSS 제외는 원문 재발행 시 복원할 수 있지만, Studio에서 삭제한 글의 영구 삭제 표식은 오래된 RSS로도 복원되지 않습니다. `0009_hide_missing_posts.sql`은 이전 6시간 유예 처리로 목록에 남은 글을 숨깁니다.

## 저장소 삭제와 접근 상태

Repository 삭제 웹훅은 블로그와 글을 즉시 공개 목록에서 숨기고 글 본문 요약·북마크/읽은 기록의 제목 스냅샷을 지웁니다. 기록 ID와 저장 시각은 남아 삭제 안내를 표시합니다. 웹훅은 원문 HMAC 서명과 delivery ID로 검증·중복 방지하며, 지연된 웹훅이나 오래된 RSS 작업이 상태를 덮어쓰지 못하도록 수집 작업의 유효성을 취소합니다.

웹훅 누락과 App 없는 블로그는 기존 5분 Cron에서 저장소 ID로 공개 접근을 확인합니다. 한 번에 최대 4개를 점검하며, 서비스 App의 유효한 설치가 있으면 메타데이터 읽기 전용 단기 토큰을 발급해 공개 저장소를 조회합니다. 대상 블로그에 App 설치를 요구하거나 사용자 토큰을 저장하지 않습니다. 설치를 이용할 수 없으면 익명 API(시간당 최대 30회)로 재시도하며, 정상 저장소는 다음 날 다시 점검합니다. 등록 수·API 제한에 따라 실제 점검 간격은 늘어날 수 있습니다. 404/410은 최소 5분 간격으로 두 번 확인한 뒤 접근 불가로 숨기며, 삭제라고 단정하거나 내용을 영구 삭제하지 않습니다. 시간 초과·5xx·인증/사용량 제한 오류는 상태를 유지하고 재시도합니다. 공개 접근 복구는 동일 저장소 ID 확인 후 조건부 캐시 없는 RSS 재검증까지 성공해야 공개됩니다. 이름이 같아도 새 저장소 ID는 별개 블로그입니다. 별도 Queues는 사용하지 않습니다.

같은 이름으로 저장소를 다시 만들어도 GitHub 저장소 ID가 다르면 별도 블로그로 등록합니다. 기존 글·북마크를 새 저장소에 옮기지 않으며 이름 변경도 ID로 확인합니다. 저장소 점검 실패 사유는 `repository_health.last_error`에 HTTP 상태나 일반화된 오류 코드만 남기고 토큰은 저장하지 않습니다.


## Studio에서 블로그 삭제

블로그 관리 → **블로그 삭제**에서 GitHub 저장소 자체를 삭제합니다. 개인 저장소 소유자만 사용할 수 있으며, 전체 저장소 이름 입력과 삭제 영향 확인이 필요합니다. Pages와 저장소의 Discussions 댓글도 사라지며 외부 배포 서비스·도메인은 별도로 정리해야 합니다. GitBlog에서 복구할 수 없습니다.

10분 유효한 확인서를 사용자·저장소 ID에 연결하고, 실행 직전 사용자 접근·소유권·공식 블로그 여부를 다시 검증합니다. 확인한 저장소 ID 하나로 제한한 단기 설치 토큰의 Administration 쓰기 권한으로 삭제하고 토큰을 폐기합니다. 같은 이름으로 다시 만든 다른 저장소에는 삭제 권한이 적용되지 않습니다. 기존 GitBlog App 권한으로 동작하며 추가 OAuth 권한은 필요하지 않습니다.

`0013_blog_deletions.sql`은 삭제 요청 ID와 상태만 기록합니다. DB 기록에 성공해야 GitHub 삭제를 요청하며 동일 요청은 재실행하지 않습니다. 성공하면 공개 목록과 저장된 제목 스냅샷을 정리하고 북마크·읽은 기록에는 삭제 안내를 남깁니다. 응답이 끊기거나 404가 반환되면 성공으로 단정하지 않고 결과 확인 화면을 표시합니다. 서명 검증된 삭제 웹훅도 미완료 요청을 완료할 수 있습니다.


## 블로그 구독과 계정 팔로우

`/following`에서 모아보기·구독 블로그·팔로잉 계정을 확인합니다. 블로그 상세의 **구독 · Star**는 GitHub Star를, `/people/<GitHub 사용자 ID>`의 **팔로우**는 GitHub Follow를 함께 설정합니다. 글 카드의 프로필은 계정 페이지로 연결됩니다.

- 기존 GitHub Star/Follow 목록은 가져오지 않습니다. GitBlog에서 직접 누른 관계만 D1에 저장합니다. 이미 GitHub에서 맺은 관계는 중복 변경 없이 로컬 목록에 추가합니다.
- 계정을 GitBlog에서 팔로우하면 해당 계정의 현재·향후 공개 블로그 글을 모아 봅니다. 블로그 구독은 선택한 저장소 하나에만 적용됩니다. 두 조건에 동시에 해당하거나 여러 번역이 있어도 한 글만 표시합니다.
- 구독/팔로우 해제는 기본적으로 GitBlog 목록에서만 지웁니다. **GitHub에서도 함께 해제**를 선택한 경우에만 GitHub Star/Follow를 제거합니다. GitHub에서 직접 변경한 관계를 GitBlog에 역동기화하지 않습니다.
- 개인 목록은 세션 사용자로 한정하고 캐시하지 않습니다. 변경에는 같은 출처 요청과 요청 제한을 적용합니다. GitHub의 고정 계정·저장소 ID를 확인한 뒤 node ID로 변경하여 이름을 재사용한 다른 대상에 적용되지 않게 합니다.
- GitHub 변경을 확인한 뒤 로컬 관계를 저장합니다. 권한 오류는 재연결을 안내합니다. GitHub 성공 후 DB 저장이 실패해도 다시 누르면 기존 외부 관계를 확인하고 로컬 저장을 마칩니다. 새 테이블에 사용자 토큰은 저장하지 않습니다.
- 이메일은 사용자가 저장소에서 **Watch → Custom → Releases → Apply**를 선택하고 GitHub 이메일 수신을 켜도록 안내합니다. GitBlog가 이메일 설정 여부를 확인하거나 대신 변경하지 않습니다. 앱 푸시 알림은 포함하지 않습니다.

배포 전 GitHub App의 **Account permissions → Followers: Read and write, Starring: Read and write**를 추가합니다. 이는 저장소 설치 권한과 별개인 사용자 승인 권한이며 기존 사용자는 GitHub 재연결로 변경된 권한을 승인해야 할 수 있습니다. 기존 저장소 설치 범위를 확대할 필요는 없습니다. `0014_social_relationships.sql`은 기존 데이터를 유지하면서 관계·잠금 테이블과 고정 소유자 ID를 추가하며, main 자동 배포에서 Worker 배포 전에 적용됩니다.

## 블로그 대시보드

Studio의 블로그 관리 화면은 권한 확인 후 최근 7일·30일의 조회수, 일별 방문자 추정치 합계, GitBlog 유입, 인기 글과 유입 도메인을 보여줍니다. 구독자·북마크는 현재 수, 댓글은 최근 7일 수입니다. 번역본은 같은 글 ID로 합산하고 글·저장소 삭제 시 방문 통계도 정리합니다.

직접 방문은 최신 템플릿의 `BlogAnalytics`에서 등록된 블로그의 `/v1/analytics/{owner}/{repo}`로 전송합니다. 기존 블로그는 템플릿 업데이트를 배포한 시점부터 수집하며 과거 방문은 복원하지 않습니다. 방문 수집을 끄려면 Studio 설정의 **블로그 방문 통계** 또는 `PUBLIC_ANALYTICS_ENABLED=false`를 사용합니다. `PUBLIC_HUB_ENABLED=false`, DNT, GPC도 수집을 중단합니다.

쿠키·로컬 스토리지를 사용하지 않고 IP와 브라우저 정보 원문을 저장하지 않습니다. 일별 HMAC으로 중복을 제외하며 같은 페이지의 반복 조회는 10분, 네트워크별 집계는 하루 1,000회로 제한합니다. 페이지·유입 URL의 쿼리는 전송하지 않고 유입은 도메인만 저장합니다. 기간 방문자 합계는 일별 추정치를 더한 값으로 기간 전체 순방문자 수가 아닙니다. 별도 Queue 없이 Workers와 D1에 직접 기록하며, 기존 예약 작업에서 31일 지난 집계를 정리합니다. 통계 조회 오류는 글 관리에 영향을 주지 않습니다.

## Blog display identity

Studio creation accepts a display title (1–100 characters) independently of the GitHub repository name, plus an optional blog image. Settings can change or remove the image. PNG, JPEG, GIF and WebP files up to 5 MB are validated by signature and request size. After administrator authorization, images are saved under `static/uploads/blog/` with a content hash filename. `PUBLIC_SITE_TITLE` and `PUBLIC_SITE_IMAGE` in `.env.production` store the display identity; uploaded images use the public repository's GitHub Raw URL. Removing an image clears its setting without deleting files or Git history.

Blog cards and the blog header share the image, falling back to the title initial when absent or unavailable. Studio also updates the identity in D1. Updated templates publish it in the deployment manifest, including for app-free blogs; older manifests preserve identities saved through Studio. Creation retries retain only the title and asset path in the encrypted receipt, never image bytes. If upload did not finish, attach the original image again to resume setup.

### Publication dates

Studio assigns `date` from the server clock on the first public save, records it in `firstPublishedAt`, and retains it on edits, hiding, and republication. Edits update `updated`. Unpublished drafts keep a provisional `date` for template compatibility and `firstPublishedAt: null`; the provisional date is replaced on first publication. Legacy public posts retain their existing date. Legacy drafts without a publication marker are treated as not yet published. Submitted date fields are ignored.

D1 `posts.published_at` is the immutable feed/ranking date, distinct from `source_published_at` (the most recently collected repository date) and `first_seen_at` (the first successful ingestion time). On first ingestion the feed date is the earlier of the source date and the server observation time. Later translations share the original post ID's date; edits, feed disappearance, and republication do not reset it. The latest list and trending age calculation both use this fixed date. A future source date does not schedule publication: an already public, validated feed item is eligible immediately. Full deletion still removes the post through the existing tombstone mechanism.

Migration `0017_publication_dates.sql` preserves historical source dates and caps future dates at migration time because historical first-seen timestamps were not recorded. It normalizes locale variants to the source language's date. Previously quarantined future items remain hidden until their public feeds are revalidated; cached feed validators are cleared and reconciliation is requested. Apply the migration before deploying the new ingestion code.

## 숏츠 탐색

`/shorts`에서 공개 글의 본문 발췌와 표지를 한 편씩 넘겨 봅니다. 모바일 세로 스크롤과 방향키·Page Up/Down을 지원하며 별도 이전/다음·순번 컨트롤은 표시하지 않습니다. 마지막 글이나 빈 피드에서 위로 충분히 당긴 뒤 놓으면 새 세션을 불러옵니다. 마우스·트랙패드도 끝에 도달한 뒤 다시 아래로 스크롤하면 같은 동작을 수행하며, 끝에 도달하는 첫 스와이프나 관성 스크롤은 새로고침하지 않습니다. 키보드는 끝에서 다음 방향키를 다시 누르거나 상단 다시 섞기를 이용할 수 있습니다. 실패한 다음 페이지는 현재 글을 유지한 채 재시도합니다. 북마크는 기존 보관함을 사용하고, **원문 읽기**는 기존 `/go/:postId`를 새 탭으로 열어 클릭 집계·읽은 기록과 연결합니다. 비로그인 사용자도 탐색할 수 있습니다.

카드와 읽기 창 모두 문단 구분을 유지합니다. 카드 본문은 고정 줄 수 대신 표지·제목·버튼을 제외한 실제 남는 높이에 맞춰 표시하며, 태블릿·데스크톱은 최대 800px 너비를 사용합니다. 카드에서 잘린 발췌는 **본문 더 보기**로 펼쳐 수집한 텍스트 전체를 읽습니다. 읽기 창에서는 스크롤·방향키가 글 넘김과 충돌하지 않으며, 닫거나 Escape를 누르면 같은 카드로 돌아옵니다. 글 소개도 잘린 경우 펼쳐 읽을 수 있고, 두 종류 모두 원문 링크를 제공합니다. 공식 템플릿은 문단 수 대신 약 800자를 목표로 발췌하며 소제목과 문단 구분을 포함해 최대 1,200자로 제한합니다.

블로그 이름 옆에는 등록된 블로그 대표 이미지를 표시하고, 이미지가 없거나 로딩에 실패하면 이름 첫 글자를 표시합니다. 너비 700px 이하의 모바일 숏츠에서는 상단 로고·검색·계정 헤더를 숨기고 하단 메뉴를 유지합니다. 모바일 하단 메뉴는 홈·숏츠·인기·내 보관함의 네 항목이며, 태블릿·데스크톱은 전체 메뉴를 표시합니다. 헤더의 실측 높이를 공통 CSS 변수로 공유하여 홈 주제 탭이 모든 화면 크기와 언어에서 헤더 바로 아래에 고정됩니다.

- `GET /v1/shorts?mode=random&cursor=...`는 한 번에 최대 12개를 반환합니다. UI 언어의 번역을 우선하고 없으면 원문 언어, 그다음 공개 번역으로 대체하여 글 ID당 하나만 노출합니다.
- 세션마다 임의 시작점을 정하고, 불변 글 ID 인덱스를 한 번 순회하면서 묶음 안의 순서도 섞습니다. 전체 목록을 매번 무작위 정렬하거나 OFFSET으로 이동하지 않습니다. 전체 글의 모든 순열을 균등 추출하는 방식은 아닙니다.
- 인증된 cursor는 시작 시각·언어·순회 경계·섞기 seed를 유지합니다. 같은 cursor의 재시도는 데이터 변경이 없으면 같은 묶음을 반환합니다. 이후 수집된 새 글은 다음 탐색에서 만나며, 삭제·비공개된 글은 매 요청에서 제외합니다. 언어 변형이나 발행일 수정으로 글이 중복되지 않습니다.
- 한 세션에서 끝까지 보면 종료 안내를 표시합니다. **다시 섞기 / 새로 둘러보기**를 눌렀을 때 새 세션이 시작되며 이전 세션의 글을 다시 만날 수 있습니다. 6시간 후에는 명시적으로 재시작해야 합니다. cursor에는 기존 `HUB_CLICK_SECRET` 또는 `AUTH_SECRET`을 용도별로 분리해 사용합니다. 응답은 `private, no-store`입니다.
- 화면에는 주변 카드만 렌더링하고 최대 60개의 글 내용을 유지합니다. 뒤로 이동은 남아 있는 버퍼 범위에서 가능하며, 다른 페이지 방문 후 브라우저 뒤로 가기는 SvelteKit snapshot으로 위치를 복원합니다. 서버에 탐색 기록이나 새 추적 쿠키를 저장하지 않습니다. 이미 내려받은 카드 내용은 실시간으로 갱신하지 않습니다.
- `src/lib/server/shorts/data.ts`는 후보 조회, `service.ts`는 순서·cursor·응답 조립, `src/lib/shorts/pager.svelte.ts`는 클라이언트 탐색 상태를 담당합니다. `ShortItem.preview`와 `ShortsPreview.svelte`를 분리하여 본문 발췌와 글 소개를 구분하며 이후 새로운 본문 형식을 추가할 수 있습니다. 추천 정책을 추가할 때는 별도 cursor 버전·후보 선택을 구현하고 기존 랜덤 세션의 순회 규칙을 유지합니다.

RSS의 선택 필드 `hub:bodyExcerpt`를 `posts.body_excerpt`에 저장하고 숏츠에서 **본문에서**로 표시합니다. 실제 Markdown의 문단 추출은 공식 Svelte 템플릿의 빌드 단계가 담당합니다. 글 소개인 `description`을 본문으로 취급하지 않습니다. 기존 템플릿은 **글 소개**로 구분하여 요약을 표시하며, 템플릿 업데이트 배포와 RSS 재수집 후 본문이 보입니다. 글 비공개·삭제 시 발췌도 숨기거나 정리하며, 발췌만 수정되어도 다음 수집에 반영됩니다. 발췌는 안전한 일반 텍스트로 렌더링합니다.

배포 전에 `0018_shorts_discovery.sql`, `0019_body_excerpts.sql`을 적용합니다. 기존 배포 스크립트는 Worker 배포 전에 D1 마이그레이션을 적용합니다. 행동 이벤트 수집·개인화 추천은 포함하지 않습니다.
