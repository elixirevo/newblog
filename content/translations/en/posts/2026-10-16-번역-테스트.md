# gitblog

Main service repository: [gitblogapp/gitblog](https://github.com/gitblogapp/gitblog).

This service allows you to create a blog using a GitHub repository and edit and publish posts. The service URL is https://gitblog.app. A single GitHub App connects file editing, Pages publishing, and Discussions comments.

## Components

- **gitblog Worker**: SvelteKit website, GitHub login, CMS, template generation, Pages configuration, and public feed API.
- **gitblog-giscus Worker**: The “Next.js/React” widget from the [original giscus fork](https://github.com/gitblogapp/gitblog-giscus). Through the `GISCUS` service binding, it provides `/client.js`, `/widget`, and the comments API on the same domain. There is no separate public domain.
- **D1 `gitblog`**: Blog/post index, click aggregation, verified comment metrics, and collection job and retry status.
- **Feed Refresh**: Verified deployment notifications trigger RSS collection immediately after a response. Since tasks are first logged in the D1 status per repository, they can be recovered even if interrupted. Cloudflare Queues are not used.
- **Cron**: Processes up to 4 failed or interrupted feed jobs and up to 8 existing browsing and comment jobs every 5 minutes. It rechecks installed repositories hourly and performs catch-up collection for normal feeds 24 hours after the last success. Daily catch-up jobs are scheduled for a maximum of 10 per run, so processing may take longer for large lists.

No Supabase service, key, or SDK is required. The previous implementation is archived in `legacy/supabase` for comparison purposes and is not used in the production runtime. A new D1 instance was created without the existing production Supabase configuration.

## Login and Creation

A single GitHub App handles login, repository creation, editing, deployment, and commenting. We do not use a separate OAuth App for creation.

1. Users log in via GitHub App authentication. The login token is maintained as an encrypted HttpOnly session cookie valid for up to 8 hours and is not stored in the server database.
2. Initially, the gitblog App is installed on the logged-in **personal account**. Both **All repositories** and **Only select repositories** are supported. Even with the selective installation option, new blogs created in gitblog are automatically added to the app’s access scope. If you select **All repositories**, the app’s permissions apply to all repositories in your account; however, blog listings, management, and feeds are limited to public repositories that have passed the template validation described below.
3. Once installation is complete, create a public blog repository in Studio by entering a name. It verifies access to the current installation using the user token, then revalidates the account ID, app ID, whether it is a personal account, the installation status (active or paused), and permissions before calling the REST template creation API using the existing GitHub App **user token**. It does not issue an installation token for creation or revoke the login token. The server’s private key is used to revalidate the current installation status.
4. After creation, verify the new repository’s access, ID, and template using the existing login session. If access is confirmed, configure environment variables, Discussions, Pages, and Actions. If the new repository is not included in the list of repositories to be installed, display **Connect the created repository**. If the user keeps “Only select repositories” selected on GitHub and adds the repository, the setup continues via the installation callback or **Continue setup after confirming connection**.
5. If automatic configuration fails, the created repository and the actual failure step are preserved, and only the configuration is retried without recreating the repository. The system distinguishes between a failed repository connection and other configuration errors and provides corresponding guidance. Requests for which no result was received from the creation process itself are not automatically retried.

On October 7, 2026, we compared the two tokens during an actual installation. While automatic access was omitted when creating a REST template with the installation token, creating both a regular repository and a template repository using the GitHub App user token resulted in both being immediately and automatically added to the existing installation. The creation process retains the user token and does not require a separate OAuth App or switching to “All repositories.” We do not use GraphQL template cloning due to permission errors. If access is lost—such as when a repository is later excluded from the installation scope—we retain the existing manual connection recovery functionality.

Even if you don’t have any repositories on GitHub, you can install the app with “All repositories” and then create your first blog in Studio. If you prefer “Only select repositories,” you can create your first blog repository on GitHub’s template creation screen and then connect only that repository to the app.

General repositories selected during installation will not be displayed in the blog list or added to the feed. Only public repositories that match the template with the values `template_repository`, `parent`, and `source` returned by GitHub are treated as blogs. Template origin, private, and archived repositories are excluded.

Studio and feed collection first verify the list of repositories to be processed, then use GraphQL to batch-query template and fork relationships in batches of up to 50. By avoiding individual REST requests for each repository, this reduces the spike in request volume observed in “All repositories.” During management and editing operations, access permissions and templates for the relevant repository are re-verified.

Studio processes up to two independent metadata queries in parallel and stores the list of identified blog IDs in the Cloudflare Cache API for 5 minutes. The cache key includes the user, app, installation, and template, along with the ID and name of the currently accessible repository. Since the installation status and the list of public and writable repositories are verified from GitHub each time, changes such as revoking access or making a repository private take precedence over the cache. The key changes when a repository is added, deleted, or renamed, and the cache is bypassed during a **list refresh** or when the list is incomplete immediately after creation. Tokens, private repositories, permission checks, and personalized HTML are not cached; in environments where the Cache API is unavailable, the system falls back to the existing real-time lookup.

The individual blog management screen checks the account, app, suspension status, and write permissions for the “All repositories” installation in real time, then queries the relevant repository directly using the user’s token. The “Selective Installation” feature reads the page until it finds the target repository and stops immediately. It continues to check public status, write permissions, and template relationships. On the Overview screen, the edit-only `.pages.yml` is not read; however, checks are performed as usual during editing and configuration tasks. The management screen displays posts and initial settings for external blogs. The comments and Pages deployment panels are not displayed, and upon entering the screen, the Pages URL or the status of Actions execution is not queried. Automatic settings for comments and Pages are retained when creating a blog.

When the “Create” button is clicked in Studio, the screen immediately switches to the “My Blogs” list and displays a loading icon on the “Creating” card. After waiting for the automatic configuration response, the “Manage” link is enabled on the blog card where access has been confirmed. For failed cards, it provides the error, instructions to correct the input, or a path to retry the remaining settings. The completion location for the creation, retry, and installation callbacks is the `/studio` list. This loading indicator reflects the status of the creation request on the current page; it is not a separate task queue that continues even if the tab is closed.

Studio stores the repository ID and name from the successful creation response in a 10-minute encrypted HttpOnly cookie tied to the user or app. If GitHub list synchronization is delayed, it displays a “Synchronizing list” card without a management link and automatically checks the list up to 5 times at intervals of 2, 4, 8, 15, and 30 seconds. Since the next check is scheduled after the current one finishes, requests do not overlap; the process pauses if you leave the screen or the list appears. If a newly created repository is not in the cached blog list, it is re-evaluated, and new blogs reflected in the list are displayed first. The creation history itself is not used as evidence of access permissions or successful configuration.

When you attach a featured image and a post cover, you can adjust the full image size, crop the area, zoom in, drag to reposition, and select left/right and top/bottom margins, as well as background color and transparency, directly in the browser’s editing window. The featured image is converted to a 512×512 static WebP file, and the cover is converted to a 1600×900 static WebP file tailored to the template’s 16:9 aspect ratio (PNG replacement supported). Files are not uploaded during editing; the cover image is saved to the user’s storage when applied, and the featured image is saved when the creation and configuration settings are saved. The featured image is optional, and undoing edits preserves the existing attachment. When retrying on the same screen after a creation failure, the edited file is retained in memory and resubmitted.

When creating a blog, the system automatically links comments to Discussions, activates Pages and Actions, saves configuration settings, and requests the first deployment. To ensure the push workflow for committing settings does not run before Pages are activated, Pages activation is completed first. Immediately after creation, if a 404 response occurs, or if there is a delay in reflecting the list of selected or full installations, or a delay in applying the default Discussions category, the system checks again up to twice after 1 or 2 seconds, respectively, for read-only operations. General permission denials and failed deployment requests are displayed immediately, while missing connections display step-by-step errors after a recheck. Pages activation and actual deployment completion are separate processes; deployment results can be verified in GitHub Actions.

Information about the created repository is stored in an encrypted cookie tied to the user and app for one hour. If the login session expires during installation, the process reverts to the original installation callback. External URLs are not allowed as login return paths.

## Blog Settings

Edit the title, introduction, author, URL, language, release, social links, Google ownership verification, and feed participation under Blog Management → **Blog Settings**. Only public values are committed to `.env.production`; existing comment IDs, repository links, and custom values are preserved. Since administrative permissions and the latest file SHA are verified, concurrent edits will not be overwritten. After committing, the template’s push workflow handles deployment. Changing the blog address does not require modifying DNS or the user’s domain on Pages.

DeepL keys are entered in a separate form, encrypted using a GitHub public key via libsodium-compatible “sealed box” encryption, and stored as the Actions Secret `DEEPL_API_KEY` in the corresponding repository. Keys are not stored in the database, cookies, or repository files, nor are they returned in error responses. The read screen only verifies whether the key is registered and cannot read the key value. Changing the key does not trigger a deployment; the change takes effect starting with the next translation run. The public setting can be used even on installations without Secrets permissions. Key deletion and other Secrets management are handled via the GitHub link.

## Saving and Publishing Posts

When you create or edit a new post in Studio and save it, you are redirected to ``/studio/[owner]/[repo]/publish``. By tracking the `deploy.yml` run on the default branch corresponding to the commit SHA in the save response, the system updates the Save → Build → Pages Deployment status approximately every 8 seconds. Once complete, a link to view the post is displayed based on the actual Pages URL; drafts do not display a public link. The “Complete” indicator is based on the success of the GitHub deployment job, and it may take a moment for the site cache to update.

If an execution is canceled due to continuous saving, it tracks the subsequent execution that includes the saved commit. If a post is edited or deleted during a subsequent run, the post will not be marked as successfully published at the time of saving. API errors are rechecked; in hidden tabs, checks are paused, and manual rechecks are available after a maximum of 20 minutes. Login and repository access permissions are revalidated with each query, and responses are not cached. The deployment status is not checked in the general post list.

## Feeds and Metrics

Public RSS feeds store only titles and excerpts; clicks redirect to the original content. The manifest must match the Pages URL and repository ID verified via the GitHub API. Redirects to other hosts or paths are rejected, and response sizes are limited. Private and archived repositories are rejected during registration. Uninstalling the GitBlog App does not unsubscribe you from public feeds. To stop collection, redistribute using ``PUBLIC_HUB_ENABLED=false`` and update the manifest accordingly. Already-registered blogs will be deactivated during the next notification or daily supplemental collection.

- Latest posts are sorted by publication time; if no language is specified, only one source language is selected.
- Popular Posts: Daily unique clicks; 1 day/7 days/30 days/All time.
- Trending: Clicks on posts from the last 72 hours, along with GitHub-verified commenters and comment counts, with time decay.
- Clicks: Excludes bots and previews; removes daily duplicates per visitor; applies a daily network cap. We do not store original IP addresses and use daily HMAC values instead. Detailed aggregates are retained for 31 days, and total cumulative sums are stored indefinitely.
- Comment Hints: We verify repositories, discussions, comments, and authors on GitHub before reflecting them. We do not trust user-submitted content or authors. Deletions also undergo GitHub re-verification.
- Tasks: D1 atomic leasing, duplicate merging, and 5 exponential retries. Failed tasks are logged in ``jobs.last_error`` and retained for 7 days. Retries are explicitly initialized by an operator in ``attempts=0`` and ``available_at=0`` for the respective tasks.

The list is read via D1 SQL, and rankings are calculated from the aggregate table. When scaling for high traffic, separate ranking snapshots and caches can be added.

## Screen Language

The service interface supports Korean (`ko`) and English (`en`). Selecting a language at the top of the screen changes the display immediately, and the selection is stored in the `gitblog_language` cookie for one year. If no selection is saved, the system reads the priority and region code (`ko-KR`, `en-US`, etc.) from `Accept-Language`; if no supported language is found, English is used.

The display language is separate from `locale` in the post filter. Post body, title, tags, and repository content are not translated or modified. If JavaScript is enabled, the page does not reload entirely when the language is changed, preserving the post you are writing. You can submit the language change form even without JavaScript.

The translation catalog is `src/lib/i18n/en.json`, and the original Korean text is used as the key. User data is inserted using the placeholders `{0}` and `{1}` and is not rendered as HTML. The screen is server-rendered in the language specified by each request, and the HTML and SvelteKit data responses for each language and user do not use a shared cache. The cache for the public feed API and static assets is maintained.

The “All,” “Latest,” “Popular,” “Trending,” and “Blog” tabs on the main screen switch between list views without redirecting to a new URL. “See More” and “Retry” are also handled within the screen, and the selected tab and any additional lists loaded are retained even when switching between tabs or changing the screen language. The top menu navigates to each list page as before.

## Reader Archive

`/library` manages bookmarks and recently viewed posts for users logged in via GitHub. PostCard’s bookmarks and the GitBlog giscus widget use the same D1 data and can be accessed via reader login without requiring a repository installation. Recently viewed posts are recorded only when you navigate to the original article via GitBlog’s ``/go/:postId``. Visits to the original article via search or other means, as well as whether you finished reading the post, are not tracked. These records are visible only to you, and you can pause, delete individual entries, or delete all records.

- `bookmarks`, `reading_history`: GitHub user ID + a language-independent fixed post ID to prevent duplicates. For posts that are temporarily inaccessible, a snapshot is retained in the user’s personal list; however, for posts deleted in Studio, all readers’ snapshots are cleared and the post is marked as “Deleted.”
- `reader_preferences`: Whether a post is in the “Recently Viewed” history. GitHub tokens are not stored in these tables.
- `github_profiles`: Shares the public GitHub profile of the repository owner (including organizations) per account. Cards, bookmarks, and read lists across multiple blogs and languages—even those with the same username but different case—use the same up-to-date profile. Organization blogs display the organization profile by default, rather than individual authors’ profiles.
- Profiles use a 24-hour cache per account, and concurrent updates are combined into a single request. When connecting an app, a temporary installation token is used; public RSS collection without an app uses the GitHub Public Profile API without authentication. Profile API errors or rate limit exceedances do not prevent post collection and preserve existing profiles. Retry feed collection or app navigation at least 1 hour after a failure. Access tokens are not stored in the database.
- `/v1/me/bookmarks`: Batch-queries post card statuses and updates bookmarks using a GitBlog session.
- `/v1/reader/bookmarks`: Allows only the retrieval and modification of post bookmark statuses using existing Giscus authentication limited to the repository. New authentication includes a user ID verified by the server, while previous authentication can continue to be used as long as GitHub verifies the user within its validity period.

The main Worker’s deployment command first applies any pending migrations, including `0002_blog_profiles.sql`, `0003_reader_library.sql`, and `0010_account_profiles.sql`. `0010` migrates the latest account-specific data from the existing blog-specific profiles, while the `blog_profiles` table is left intact to allow previous Worker requests to complete. Next, deploy the `gitblog-giscus` Worker. Profiles will be populated during the next feed synchronization. Blogs using the existing GitBlog comment host will receive the bookmark UI without any template modifications.

## Deleting Posts

On the existing post editing screen in Studio, select **Confirm Deletion**. You must verify the list of original and translated posts in `content/translations/<locale>/posts/<같은 파일명>` and enter the filename before deletion can proceed. The server re-verifies the GitHub App installation and user write permissions; if the branch HEAD or the original post’s SHA has changed since verification, the process is halted. The original post and its translations are reflected in a single deletion commit, and forced pushes are not used. Existing templates can also be used without separate modifications, and the existing deployment workflow runs after the commit.

The `0004_post_deletions.sql` migration is required. Upon deletion, all language-specific feed data, comment counts, and click counts for the post are cleared, and snapshots—including the title, summary, and URL—are removed from all readers’ bookmarks and reading histories. Only the ID of the deleted post and the time it was saved or visited will remain in personal lists. The deletion flag prevents previous RSS feeds or late bookmark requests from re-saving the information. Even if you restore the same post ID from Git, it will not be automatically re-registered; therefore, you must use a new post ID to republish it.

To prepare for potential disruptions between GitHub and D1, only the commit SHA, repository, path, and processing status are first recorded in `post_deletions`. User tokens and post content are not stored. If GitHub responses or database cleanup are interrupted, the status will show as “Pending” rather than “Completed.” A Cron job running every five minutes uses an installation token with read-only access to the “Contents” of a single repository to verify whether a deletion commit has been included in the target branch, then completes the cleanup. If the installation has been revoked and verification is not possible, the status remains “Pending.”

This feature performs a **general deletion**. It does not remove past Git history, GitHub Discussions, Releases, shared images, or external copies. Content on public sites disappears after redistribution is complete, and cached feed responses disappear after the cache expires. If distribution fails, GitHub Actions must retry. Posts deleted directly from GitHub or the Pages CMS follow the existing missing feed policy and do not undergo the same snapshot cleanup as explicit deletions in Studio.

### Removing posts from Git history

On the post deletion screen in Studio, select **Analyze to remove from Git history**. You can also proceed to **Remove from Git History** from the screen that appears after completing a standard deletion. This feature is available only to repository administrators. To execute it, you must review the analysis results (file paths, branches, tags, and number of commits) and submit the `owner/repository/filename.md` token along with the confirmation checkbox. The analysis remains valid for 30 minutes.

Execution is handled by **GitHub Actions in the target blog repository**. The template’s ``.github/workflows/post-history.yml`` calls ``post-history-worker.yml`` from the public template repository (``gitblogapp/svelte-gitblog-template``) by pinning it to a specific commit SHA. Run history, logs, and Actions usage are associated with the blog repository, and the GitBlog App only needs to be installed on that specific blog. There is no need to install the App on `gitblogapp/gitblog` or store the App’s private key or PAT on the blog. The job only checks out the pinned public run code and does not execute any scripts within the blog.

Operational Preparation:

1. **First, push** the execution code, reusable workflows, and caller commits from the template repository to a public remote. Approved commits are pinned to `src/lib/server/history/runner-version.ts` and must match the SHA of the template caller’s `uses`. When updating the execution code, publish in the following order: the template’s public execution code → the template’s reusable workflow → the approved SHA of the template caller and the server.
2. Publish the template and deploy the Worker by applying the D1 migration up to `0005_history_purges.sql`. The existing `bun run deploy` and Workers Builds commands apply the migration before deployment.
3. New blogs receive the execution workflow from the template. **Existing blogs must add the `.github/workflows/post-history.yml` file from the latest template to the default branch.** If the file already exists, review the existing changes and merge them. If there is no workflow or the version differs, Studio will guide you through the update.
4. Enable Actions on the target blog and allow public calls to the `gitblogapp/svelte-gitblog-template` reusable workflow. The GitBlog App on that blog requires existing “Contents” and “Actions” write permissions, and the requester must have administrator permissions. Use only the existing Workers Secret for the App’s private key.
5. The execution workflow calls the production workflow ``gitblog.app``. Tasks created in the local database are not linked to the production callback. When forking to a different service domain, update the `origin` in the template’s ``scripts/history/run.py``, the server’s OIDC audience, the public reusable workflow, and the approval SHA together.

Analysis searches for the post’s fixed ID in Markdown files across all branches and tags, and includes translations with the same filename and Git-detected renaming paths. Files whose names and content changed significantly before IDs were introduced, or documents that were copied separately, cannot be automatically linked. Automatic processing is rejected if the same path is used for a different post ID or if the file has been moved outside the post folder. It supports up to 100 references, 5,000 commits, 20,000 Markdown blobs, 500,000 tree entries, and 500 removal paths; processing will stop if these limits are exceeded.

After verification, the same analysis is run again to check if the results match, and the changes are applied all at once using ``git push --atomic`` and ``--force-with-lease=<ref>:<old SHA>`` per reference. Unconditional force/mirror pushes, branch protection removal, and PR reference changes are not performed. If branch or tag protection rules or permissions are denied, the user must review the settings. Commit/tag signatures may be lost, and subsequent commit SHAs will change. Collaborators must clone the repository anew or rebase safely; merging the old branch may restore the deleted content.

Verify the GitHub OIDC signature, issuer, audience, the repository ID of the target blog, the caller path, the commit SHA at the time of analysis, the event,run ID/attempt, and verifies that `job_workflow_ref` and `job_workflow_sha` are the exact SHAs of approved reusable workflows. An installation token, limited to that single blog, is granted only for such operations. User tokens are not stored in the database. Analysis tokens are read-only and allow writing to `Contents` only for verified deletion operations. Installation tokens are attempted to be discarded upon job completion and expire after GitHub’s short validity period, even if the job is forcefully terminated. Re-run Actions jobs are not approved.

Before a push, the approved change log is recorded in D1, and the deletion mark on the post ID is finalized only after it is confirmed that all branches and tags match the results or that a branch has added a subsequent commit on top of the deletion result. At this point, the feed, snapshots of all readers’ bookmarks and reading history, and aggregated data are cleaned up, just as with the existing deletion feature. Pinned IDs and bookmarks for other posts are retained. Lost callbacks are recovered by the status screen and the 5-minute periodic task. If the result changes due to concurrent modifications, the task is not marked as successful and remains in a pending verification state. If verification for a completed task remains pending, an administrator must inspect the actual refs and execution logs. After completion, a redistribution request is made, and any redistribution failures are indicated separately.

If an execution request is explicitly rejected, the reason for failure is displayed immediately. Response losses and server errors are verified via GitHub execution logs without retrying. The status screen automatically refreshes every 10 seconds starting 5 seconds after the request, pauses polling in hidden tabs, and stops when complete. GitHub job failures, cancellations, and missing callbacks are detected on the screen. If no execution history appears for 10 minutes, the process is treated as a failure to allow for reanalysis; however, verification-pending tasks that are already prepared for a push are not terminated in this manner.

**Scope of Removal:** All versions of the selected Markdown path are removed from branches and tags. Text written directly in commit messages, comments in Discussions, text and attachments in Releases, shared images, past Actions artifacts and deployments, PR references, external clones and forks, and search engine and GitHub caches are not deleted. We do not guarantee that the objects themselves will disappear immediately from GitHub. Cache removal for sensitive data follows the [official GitHub guidelines](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

Verification of actual Git changes is performed in a temporary bare repository instead of the production repository:

```sh
cd ../svelte-gitblog-template
python3 -m venv /tmp/gitblog-history-venv
/tmp/gitblog-history-venv/bin/pip install -r scripts/history/requirements.txt
PATH="/tmp/gitblog-history-venv/bin:$PATH" bun run test:history
cd ../gitblog

```

## Studio Template Update

Proceed in the following order: Blog Management → Check for stable versions in **Template Update** → Analyze changes → Prepare an update PR → Verify via Actions → Apply after confirmation. Only administrators of the target blog repository can use this feature. The GitBlog App is installed only on the target blog; no additional PAT or user tokens stored on the server are required.

In the template’s default branch, ``.gitblog/release.json`` points to the stable version and its **exact commit SHA**. Code changes in ``main`` that have not yet been released are not included in the update. Template maintainers must first complete and commit code changes and verify `bun run update:check`, then update `version` and `revision` in the release in a separate commit. You must first make the unpushed commits for the service and template public before using the feature.

For a template creation blog being updated for the first time, the files in the initial creation commit serve as the baseline. Subsequently, comparisons are made based on the official template revision of ``.gitblog/template.json`` stored in the update PR. Custom fields in the version history are preserved. The system does not automatically infer the creation criteria for forks, multiple root histories, or the initial version of repositories with 500 or more commits. In such cases, the administrator must review the official template SHA that served as the actual basis, register the corresponding file on the default branch, and then re-analyze the data. Arbitrarily entering the latest SHA will not provide a valid basis for comparison.

```json
{
  "schemaVersion": 1,
  "repository": "gitblogapp/svelte-gitblog-template",
  "version": "1.0.0",
  "revision": "실제로 적용한 공식 템플릿의 40자리 커밋 SHA"
}
```

Compare the previous official file, current blog, and new official file **on a per-file basis**. Only additions, changes, and deletions to the unmodified official file are reflected, while user-added files, source text, translations, media, settings, CMS, themes, and extensions are preserved. The preservation rules for the previous, current, and new templates are combined and applied; the default protected paths cannot be reduced. Code, dependencies, lockfiles, and workflows modified on either side are marked as conflicts without automatic line merging. You must merge the changes while preserving user modifications on GitHub and then reanalyze them. Changes to the pre-theme-separation structure, theme/extension API changes, binary files, symlinks, and large-scale changes are suspended as separate migration targets. Code validation alone does not guarantee visual consistency on the user interface.

Only the analysis results, the SHA of the approved commit, and the PR number are stored in D1 `0006_template_updates.sql`. Source code, secret keys, and GitHub tokens are not stored in the database. If the connection is lost during preparation, the system will retry the same task and reuse the existing branch and PR. The default branch is not changed during the preparation phase, and branches are not force-pushed. The task ends by closing any open PRs and allowing new analyses. Code that has already been merged from an external source is not reverted, nor are branches deleted.

Before applying, the system re-verifies the current administrator permissions, the repository, branch, and head SHA of the saved PR, the default branch SHA at the time of analysis, the successful execution of the corresponding PR on the official `validate-update.yml`, the success of the actual validate job, and the “clean” merge status on GitHub. If a new post is created or the PR branch is changed after analysis, the analysis must be performed again. Merge only using the approved head SHA, and the repository’s existing push deployment workflow will handle the redeployment. GitBlog does not call translation, ID generation, or publishing commands during the preparation process. If the user has added any push or PR workflows, their execution rules will also apply and must be reviewed.

Operational Preparation: Apply D1 migration 0006; add **Write to Pull Requests and Workflows** permissions for the GitBlog App, approve its installation, allow Actions execution, and publish the service and templates. “Write to `Actions`” and “Write to `Workflows`” are distinct permissions. Use the existing deployment command as-is to apply automatic migration during the build.

## Update the feed after blog registration and deployment

Merge the three paths into a single GitHub repository ID. When a repository is created on the web, it is immediately registered in D1 with the status `pending` and instantly displayed in My List based on existing Studio creation records. Even if the connection to comments or Pages fails, the repository that has already been created will not be recreated. In the public list, it is displayed as `active` after verifying a valid deployment manifest and RSS feed.

Blogs using official templates without an app can also be automatically registered after deployment. The template’s `register` action triggers the official `register-blog.yml` as a fixed commit. This job checks the blog’s visibility status, official template/fork relationship, default branch, and Pages URL using a temporary `GITHUB_TOKEN` in the calling repository, and transmits GitHub Actions OIDC credentials. The server verifies the signature, audience, repository ID, and the fixed SHA of the official workflow. GitHub access tokens are neither sent to nor stored by the server. The trust boundary is that the code in the blog is not executed within the fixed registration action.

- Use `PUBLIC_HUB_ENABLED=true` and `PUBLIC_HUB_URL=https://gitblog.app` from `.env.production`. The GitHub Actions policy must allow reused workflows based on the official template and `id-token: write`.
- If the first notification delivery fails, the workflow will retry up to four times. If all attempts fail, manually run **Sync GitBlog feed** in Actions or re-register it for the next deployment. Repositories with no app and no successful notifications cannot be discovered automatically.
- Repositories containing official templates or forks with the GitBlog App installed are also registered through the existing hourly crawl. Once the Pages URL is verified, app installation is not required for public RSS updates.
- Unauthenticated notifications from older templates will continue to be processed only for repositories that are already registered. A new template workflow is required for initial registration without an app.
- Verified notifications are limited to 12 per minute per repository. They do not share the global 30-per-minute limit for existing anonymous notifications. Resending notifications within the same execution does not create duplicate work.
- If deployment commits are included in the manifest and each RSS feed, and previous results remain on the CDN, this is not mistaken for a success. When a new notification arrives, saving the previous collection results is blocked, and the latest deployment is processed.
- Failed collection attempts are logged in D1 and retried at intervals ranging from 2 minutes to a maximum of 6 hours. Posts that have not changed are not rewritten, and daily supplemental collections use ETag/Last-Modified. Costs are included in existing Workers request and CPU usage, as well as D1 read and write usage, and free usage is not guaranteed.

You must apply ``0007_blog_ingestion.sql`` before deploying the Worker. The crawl status of existing registered blogs will also be carried over to this migration. `0008_ingestion_indexes.sql` separates recovery tasks from normal feed indexes to reduce database reads during scheduled runs. When changing the trusted SHA for the registration workflow, first publish a commit to the public template, then update the server’s `ingestion-identity.ts` approval SHA along with the new template call.

Articles that have disappeared from RSS are immediately hidden in `removed` during a successful collection where all language feeds have been validated. RSS errors, partial collection failures, and previous deployment commits are not used as grounds for deletion. General RSS exclusions can be restored when the original text is republished, but the permanent deletion flag for posts deleted in Studio cannot be restored even via old RSS feeds. `0009_hide_missing_posts.sql` hides posts that remain on the list due to the previous 6-hour grace period.

## Repository Deletion and Access Status

The repository deletion webhook immediately hides the blog and posts from the public list and clears the post body summaries and title snapshots from bookmarks and reading history. The record ID and save time remain to indicate the deletion notice. The webhook verifies authenticity and prevents duplicates using the original post’s HMAC signature and delivery ID, and invalidates the collection task to ensure delayed webhooks or outdated RSS operations cannot overwrite the status.

For blogs without the app or those where the webhook is missing, public access is verified via the repository ID using the existing 5-minute Cron job. Up to four blogs are checked at a time; if a valid installation of the service app is detected, a read-only short-term token for metadata is issued to query the public repository. The service does not require the target blog to install the app or store user tokens. If installation is unavailable, the system retries using the anonymous API (up to 30 times per hour), and valid repositories are checked again the following day. Actual check intervals may increase depending on the number of registrations and API limits. For 404/410 errors, the system checks twice at least 5 minutes apart before marking the content as inaccessible; it does not assume deletion or permanently delete the content. For timeouts, 5xx errors, and authentication/quota errors, the status is retained and the system retries. Public access is restored only after verifying the same repository ID and successfully revalidating the RSS feed without caching. Even if the names are identical, a new repository ID constitutes a separate blog. No separate queues are used.

Even if a repository is recreated with the same name, it is registered as a separate blog if the GitHub repository ID is different. Existing posts and bookmarks are not transferred to the new repository, and name changes are also verified by the ID. For repository inspection failures, only the HTTP status or generalized error code is logged in `repository_health.last_error`; tokens are not stored.

## Deleting a Blog in Studio

Go to Blog Management → **Delete Blog** to delete the GitHub repository itself. This feature is available only to the owner of the private repository and requires entering the full repository name and confirming the implications of deletion. Comments on Pages and in the repository’s Discussions will also be deleted, and any external hosting services or domains must be cleaned up separately. This action cannot be undone in GitBlog.

A verification token valid for 10 minutes is linked to the user and repository IDs, and user access, ownership, and official blog status are re-verified immediately before execution. Deletion is performed using the Administration write permission of a short-term installation token—limited to a single verified repository ID—and the token is then discarded. Deletion permissions do not apply to other repositories created with the same name. This operates using existing GitBlog App permissions; no additional OAuth permissions are required.

`0013_blog_deletions.sql` logs only the deletion request ID and status. It requests deletion from GitHub only after successfully logging the entry in the database and does not re-execute the same request. Upon success, it clears the public list and saved title snapshots, and leaves a deletion notice in bookmarks and read history. If the connection is lost or a 404 error is returned, the operation is not considered successful, and a result confirmation screen is displayed. A signed, verified deletion webhook can also complete an incomplete request.

## Blog Dashboard

After verifying permissions, Studio’s blog management screen displays page views for the last 7 and 30 days, total estimated daily visitors, traffic from GitBlog, popular posts, and referring domains. Subscribers and bookmarks show current counts, while comments show the count for the last 7 days. Translated versions are aggregated under the same post ID, and visit statistics are cleared when a post or repository is deleted.

Direct visits are transferred from `BlogAnalytics` in the latest template to `/v1/analytics/{owner}/{repo}` for registered blogs. Data for existing blogs is collected starting from the time the template update is deployed; past visits are not restored. To disable visit tracking, use **Blog Visit Statistics** in Studio settings or `PUBLIC_ANALYTICS_ENABLED=false`. `PUBLIC_HUB_ENABLED=false`, DNT, and GPC tracking will also be stopped.

We do not use cookies or local storage, nor do we store raw IP or browser information. Duplicate visits are excluded using a daily HMAC; repeat views of the same page are limited to 10 minutes, and aggregation per network is capped at 1,000 visits per day. We do not transmit page or referral URL queries; for referrals, only the domain is stored. The total number of visitors for a given period is the sum of daily estimates and does not represent the total number of unique visitors for the entire period. Data is recorded directly to Workers and D1 without a separate queue, and aggregates older than 31 days are purged from existing scheduled jobs. Errors in statistical queries do not affect post management.

Studio creation allows you to specify a display title (1–100 characters) independently of the GitHub repository name, plus an optional blog image. Settings can be used to change or remove the image. ### Publication Dates

Studio assigns `date` based on the server clock upon the first public save, records it in `firstPublishedAt`, and retains it during edits, hiding, and republication. Edits update `updated`. Unpublished drafts retain a provisional `date` for template compatibility and `firstPublishedAt: null`; the provisional date is replaced upon first publication. Legacy public posts retain their existing date. Legacy drafts without a publication marker are treated as not yet published. Submitted date fields are ignored.

D1 `posts.published_at` is the immutable feed/ranking date, distinct from `source_published_at` (the most recently collected repository date) and `first_seen_at` (the time of the first successful ingestion). Upon initial ingestion, the feed date is the earlier of the source date and the server observation time. Subsequent translations retain the original post ID’s date; edits, feed removal, and republication do not reset it. Both the latest list and trending age calculations use this fixed date. A future source date does not schedule publication: an already public, validated feed item is eligible immediately. Full deletion still removes the post via the existing tombstone mechanism.

The `0017_publication_dates.sql` migration preserves historical source dates and caps future dates at the time of migration because historical “first-seen” timestamps were not recorded. It normalizes locale variants to the source language’s date format. Previously quarantined future items remain hidden until their public feeds are revalidated; cached feed validators are cleared, and reconciliation is requested. Apply the migration before deploying the new ingestion code.

## Explore Shorts

In `/shorts`, you can scroll through excerpts from public posts and their cover images one at a time. It supports vertical scrolling on mobile devices as well as arrow keys and Page Up/Down, and does not display separate “Previous,” “Next,” or “Number” controls. If you pull up far enough from the last post or an empty feed and then release, a new session is loaded. With a mouse or trackpad, reaching the end of the feed and scrolling down again performs the same action; however, the first swipe or inertial scroll that reaches the end does not trigger a refresh. On a keyboard, you can press the next arrow key after reaching the end or use the “Shuffle” button at the top. If the next page fails to load, it will retry while retaining the current post. Bookmarks use the existing archive, and **Read Original** opens the existing `/go/:postId` in a new tab, linking it to click counts and reading history. Non-logged-in users can also browse.

Both the card and the reading pane preserve paragraph breaks. The card body is displayed based on the actual available height—excluding the cover, title, and buttons—rather than a fixed number of lines, with a maximum width of 800px on tablets and desktops. Truncated excerpts on the card can be expanded via **Read More** to view the full text. In the reading pane, scrolling and arrow keys do not interfere with page navigation; closing the pane or pressing Escape returns you to the same card. If the article introduction is truncated, you can expand it to read the full text, and both types of content provide a link to the original article. The official template aims for excerpts of approximately 800 characters instead of a set number of paragraphs, with a maximum limit of 1,200 characters, including subheadings and paragraph breaks.

The registered blog’s featured image is displayed next to the blog name; if no image is available or fails to load, the first letter of the name is displayed instead. On mobile Shorts with a width of 700px or less, the top header (logo, search, and account) is hidden, while the bottom menu remains visible. The mobile bottom menu consists of four items: Home, Shorts, Popular, and My Collection, while tablets and desktops display the full menu. The actual height of the header is shared as a common CSS variable so that the Home topic tab remains fixed directly below the header across all screen sizes and languages.

- `GET /v1/shorts?mode=random&cursor=...` returns up to 12 items at a time. It prioritizes translations in the UI language; if none is available, it falls back to the source language, and then to public translations, displaying only one per post ID.
- A random starting point is determined for each session, and the order within each batch is shuffled while iterating once through the immutable post ID index. The entire list is not randomly sorted or shifted by OFFSET each time. This method does not evenly sample all permutations of all posts.
- An authenticated cursor retains the start time, language, iteration boundary, and shuffling seed. A retry with the same cursor returns the same batch if the data has not changed. New posts collected afterward will appear in the next exploration, and deleted or unpublished posts are excluded from every request. Posts do not appear duplicated due to language variations or publication date modifications.
- If you view all posts in a single session, an end-of-session notification will appear. Clicking **Shuffle Again / Start Over** begins a new session, and you may encounter posts from the previous session again. After six hours, you must explicitly restart the session. The `cursor` uses either ``HUB_CLICK_SECRET`` or ``AUTH_SECRET``, separated by purpose. The response is ``private, no-store``.
- The screen renders only nearby cards and retains the content of up to 60 posts. You can navigate backward within the remaining buffer range, and using the browser’s “Back” button after visiting another page restores your position using a SvelteKit snapshot. No browsing history or new tracking cookies are stored on the server. The content of cards that have already been downloaded is not updated in real time.
- `src/lib/server/shorts/data.ts` handles candidate lookups, `service.ts` handles order, cursor, and response assembly, and `src/lib/shorts/pager.svelte.ts` manages the client’s navigation state. By separating `ShortItem.preview` and `ShortsPreview.svelte`, we distinguish between content excerpts and article introductions, allowing for the addition of new content formats in the future. When adding recommendation policies, implement separate cursor versions and candidate selection while maintaining the existing random session traversal rules.

The RSS selection field `hub:bodyExcerpt` is stored in `posts.body_excerpt` and displayed as **"From the body"** in Shorts. The actual extraction of Markdown paragraphs is handled by the build phase of the official Svelte template. The post introduction (`description`) is not treated as part of the main text. The existing template distinguishes it as **Post Introduction** and displays a summary; the main text will be visible after the template update is deployed and the RSS feed is re-crawled. When a post is set to private or deleted, the excerpt is also hidden or cleaned up, and even if only the excerpt is modified, the changes will be reflected in the next crawl. Excerpts are rendered as safe plain text.

`0018_shorts_discovery.sql` and `0019_body_excerpts.sql` are applied before deployment. The existing deployment script applies the D1 migration before Worker deployment. Behavior event collection and personalized recommendations are not included.
